# 1. What this is

**ScopeCrete** is a mobile-first PWA being built by **Coy Sacco**, a concrete contractor in Baton Rouge, Louisiana. It replaces a receptionist.

Every call and text into the business lands in it, gets understood, and turns into priced work. The intended chain:

> a stranger calls → the system understands what they want → a job exists → a scope is built → an estimate goes out → follow-up happens without being remembered

He is building it for his own business first. Selling it to other contractors is a later, unproven question.

**He wants blunt risk assessment, not encouragement.** Tell him when something is wrong.

# 2. Standing rules — these are not negotiable

These came from real failures on this project. Each one cost a day or more.

1. **Only change what is requested.** No opportunistic refactors.
2. **Never report work done until verified.** Against production, not the working tree.
3. **If you cannot verify from your sandbox, say so.** Mark it UNVERIFIED and name the pass condition.
4. **Read files in full before acting.** A route was once reported after reading its first thirty lines; the fabricated response was on line sixty.
5. **Never keep or delete code based on a name or a docstring.** A comment claiming a link was "verified alive" was true and irrelevant.
6. **Check RLS before writing a query.** A query verified as service role returns different rows through a session client.
7. **A migration or a merge to `master` happens only when Coy says so in that conversation.** Not a standing grant.
8. **No mock data ships. No fabricated numbers, ever.**

## Rule 8 in detail, because it is the one that keeps being broken

**A hardcoded fallback is not a live value.** If the code can produce a number with the database empty, it is a placeholder and must render as one.

Things that have actually shipped to Coy's phone and were fabricated:

- an invented person, "Clay Jensen", on the profile screen
- `$36.6k` pipeline value and `50%` win rate, both from mock constants
- `Off the top 11%` on the Cash screen, from `: 11` in a route, next to six fields correctly showing "—"
- `$0` cash position — an assertion the account is empty, when the truth is nobody has recorded what is in it
- `HTTP 200` and a fabricated lead id from `api/leads`, so a customer saw a confirmation for a lead never written

**A screen that invents a number is worse than one that says it has none.** An empty state holds the layout and says what it is waiting for.

**And a pass condition must be falsifiable.** "Cash shows a real off-the-top percentage" cannot fail. "Off-the-top shows a dash, because `org_cost_settings` is empty" can. Every check you write states its failure mode next to it.

# 5. Architecture — the settled decisions

## 5.1 The spine

**`messages` is the spine.** One table, every channel. `quo_events` is the universal raw log holding every event with its full payload.

*There is no raw log to build — there is one to promote.*

Projection from raw to spine happens in a **database trigger**, not application code: `quo_events_project` → `sc_quo_events_project()` → `sc_project_raw_event()`. Migration 016 moved it there. **Nothing else may write to `messages`** beyond the glance-line summary.

`sc_spine_drift` is a view counting events that arrived but never reached the app. **It currently shows 1.** The UI surfaces it as a banner.

## 5.2 Direction

*Ownership decides direction; the provider label is a claim.*

`sc_resolve_direction` reads `org_phone_numbers` (3 rows) and asks which number belongs to the org. The provider's own inbound/outbound label is not trusted — migration 018a repaired **215 rows whose addresses were swapped**.

## 5.3 Contacts and classification

Four buckets: **customer, vendor, personal, spam**, plus `contact_subtype` from `org_contact_subtypes` (14 seeded).

*Buckets are code, subcategories are data.*
*Money in is a customer, money out is a vendor.*

**Names never go to `contacts.name`. Ever.** They go to `contact_name_claims` with a claim type (`self_identification`, `signature_block`, `provider_guess`, `greeting`, `third_party_mention`) and the message they came from.

*Every extracted name arrives with its receipt.*

**The Corey trap** is the acceptance test: one transcript contains both "Hey, Carlos" and "Hey, Corey". Both are `greeting`. Neither becomes a name.

## 5.4 Jobs

**`jobs` is the hub of the work side — 19 tables carry a `job_id` foreign key.** Everything downstream is gated on it.

- A job requires only `org_id`. `status` **defaults to `'lead'`**.
- **A job is the container from first contact onward, not the reward for winning.** `won_at` / `lost_at` / `declined_at` arrive later.
- Contact type is decided **once**. A job is an **event** — a repeat customer generates one per request. The trigger is *a request for work appearing in a thread*, not the setting of `contact_type`.

**Coy's ruling: creation is implicit.** "If there is enough information for a scope to be added, then there is enough info for a job creation."

Provenance columns added 29 Aug and verified live:

| column | meaning |
|---|---|
| `origin` | `'manual'` or `'machine'`, CHECK-constrained, defaults `'manual'` |
| `created_from_message_id` | FK to `messages` — what the machine read |
| `confirmed_at` / `confirmed_by` | when Coy accepted a machine job. NULL = unreviewed |

**Pipeline value counts `origin='manual' OR confirmed_at IS NOT NULL`.** An unreviewed machine job is **visible but uncounted**.

*A machine opinion changes what you are asked, never what you are shown.*

## 5.5 Scopes

**There is no `scopes` table.** A scope is `job_sections` rows under a job, priced through `estimates` + `estimate_line_items` (which points at `job_sections`).

A driveway + patio + demo at one property is **one job, three sections**.

### THE RULE ON AI-BUILT SCOPES

**A machine-built scope writes to `job_sections` — the same rows the scope builder reads and edits. No draft table, no staging area, no separate "AI scope" representation.**

Coy opens the scope builder on site and changes the numbers with a tape measure in his hand. Same table, same screen, same edit path. The only difference is provenance metadata on the row.

A separate staging table gives a scope two places to live, and the first time they disagree he prices off the wrong one.

## 5.6 RLS

**`get_user_org_ids()` is the isolation primitive.** Migration 024 moved **55 policies across 22 tables** off a dead `current_setting('app.current_org_id')` GUC.

**Views must set `security_invoker = true`** (PG17) or they run as owner and bypass RLS. `sc_spine_drift` and `sc_open_name_questions` do **not** have it — latent cross-tenant leaks, currently harmless at one org.

## 6.2 The classification trap — READ THIS

`contact_type` **DEFAULTS to `'customer'`** and `classification_source` **DEFAULTS to `'legacy'`**.

So 166 of 173 contacts read as "customer" and **171 are `classification_source='legacy'`**. **Nothing has actually been classified.** Luis (a subcontractor, 323 messages), Ace Hardware, Dalton Digital and the lead-gen line are all sitting in the database as customers because nobody told it otherwise.

**A UI rendering a CUSTOMER badge off that column is showing a fabricated classification.** This is rule 8 one layer deeper — the fallback is in the schema. Treat *unclassified* as its own state.

## 6.3 The call text problem

**Only 54 of 528 calls carry any summary text.** The rest are a number and a timestamp.

This blocks everything downstream. Extraction over a thread missing most of its calls produces a confident fact sheet built on a fraction of the conversation — **which is worse than none, because it looks complete.**

## 6.4 What works today

Threads. Real, and proven end to end. Coy opens his phone and sees genuine conversations: named and unnamed contacts, call summaries, voicemail glance lines, transcripts on expand, the drift banner. Newest-first ordering. Honest empty states on Scope, Cash and Pipeline.

The spine, the projection trigger, the voicemail fetch and session auth all work.
